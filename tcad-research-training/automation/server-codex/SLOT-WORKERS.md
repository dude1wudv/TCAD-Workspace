# 十三槽派发与收集

`dispatch_mode: "slot_workers"` 启用新执行接口。运行器在虚拟机封存原始结果，写入带摘要和字节数的回执，再归还计算槽。服务器在独立通道取回并校验归档。任务的正式依赖仍等工程收集通过，科学验收沿用实验合同。旧意图继续按原协议收集。

## 备料和轮换

- 私有策略设置 `planner_mode: "disabled"`，由唯一控制器发布 `scheduler_supply.waves` 指定的波次。每个引用使用工作区相对 `path` 和 `sha256`，波次采用 `tcad-r06-development-wave-v1`，每份含 1–13 个单任务 `proposal` 引用。正式波次可用原 `prepare-wave` 生成。定版策略可引用最多 32 份已批准的波次。
- 首版自动供料复用已冻结的 D0–D3 正式开发和输运配方。开发原始数据使用 `raw-dev-` 任务及独立项目目录。用 `prepare-raw-wave <提案相对路径> [...]` 生成与完整输入摘要绑定的波次。两个准备命令均只打印清单。程序分后端与核数维持一波已就绪的任务，正式优先，同级按入队顺序。
- 缺配方、实验依据或需要修复时，`explain` 显示待办和阻塞原因。科研人员或 AI 可独立整理新输入和提案，审核冻结后才纳入波次。保留原案例、事件和修复谱系。启用自动供料时使用独立的 AI 提案流程；生产进程内的 Codex 规划器具有旧队列写权，因此与自动供料模式互斥。
- 将 `pool_switching.dependency_mode` 设为 `true` 以启用按依赖轮换。批准任务用 `depends_on` 指向明确的输运任务，并用 `requires` 声明所需产物。可运行的前置输运任务组成一批。当前池释放后运行该批，Geant4 并发以现有配置为限。租约冲突保留证据并报告。人工排空入口继续用于处理例外。

## 发布和回滚

1. 从审阅通过的提交打包：`python -B automation/server-codex/package.py --runtime-only --slot-workers --output <新包路径>`。在 TCAD 服务器以原安装器的 `--stage-runtime-only` 校验包和逐文件摘要。版本目录 `runner-source/` 中有与控制器配套的原运行器源码。
2. 先核对生产发布版本、策略所有权、原 run 和原锁。由原调度服务暂停新增，等求解自然结束并由原协议完成收集。确认旧服务停止、租约释放、相关锁空闲、无未登记求解器。备份旧版本、策略和受影响的源码文件，由现任服务器维护者将配套源码部署到原工作区，按私有配置切换版本。保留当前工作区其余文件和全部运行账本。
3. 先以 `check` 与 `reconcile --read-only` 对账，确认原 ID、运行器版本、一致的锁和资源读数。逐档启用 1 → 4 → 8 → 13。每档用获准任务验证原生启动、封存、释放、收集完整链路。记录真实完成、资源水位、等待原因和补位延迟。
4. 13 槽档观察至少 24 小时和 20 次真实补位，其中至少一次是四核槽补位。记录槽释放到下一项原生启动的时间，报告样本数、典型值和 P95。资源及同规格任务均就绪时，P95 目标为 60 秒。收集积压和科学验收各按实际证据报告。
5. 回滚先暂停新增，继续使用新版对账并处理新版封存与收集，直至在途 run 全部收集释放。逐项验证旧版能读取变更期间新增的结果与状态，再切回代码和配置。证据或身份未核实时维持暂停并保留原租约。运行账本始终使用当前版本的实际记录。

状态看板沿用原 `live.json` 与 `status.json`。新版观测附带按核数的槽位和等待原因，以及收集积压数量与最久等待时间。公开字段经过白名单转换，旧或过期数据按相应状态显示。
